# Orchestration

How a turn works inside the backend: how the orchestrator hands off work, what
the agent sends and streams back, and how that output becomes UI.

## Orchestrator

The bridge between UI and the agent. It runs on IDA main thread, so its
job is to start the work and get out of the way, never to block.

Each prompt, it:

1. Gathers the current IDA context (function, disassembly, pseudocode, xrefs at
   the cursor).
2. Hands the prompt and context to the agent as a background task.
3. Routes the agent's streamed output back to the renderer as it arrives.

It also holds the small amount of per-turn state the renderer needs, so the
renderer itself can stay stateless.

## Agent

The agent talks to the llm provider. Runs on the worker thread.

It is given four things: the user prompt, the IDA context, the available tools,
and the session history. From those it builds and streams the model, yielding
output piece by piece until the response ends.

### Prompts

Two prompts shape every turn, and they land in different places:

- **System prompt** — the agent's standing instructions, applied to every turn:
  its role inside IDA, when to call a tool versus answer directly, and rules
  against inventing addresses or names. It defines who the agent is, and is not
  part of the conversation history.
- **User prompt** — this turn's input message: the user's text plus the IDA
  context. This is what gets added to the session history.

<Callout>
The system prompt is a living file, not a spec. It is expected to grow and
change. Read `backend/chatbot/task/content/system_prompt.md.jinja` for what it
says today.
</Callout>

### Tools

Each turn, the agent is handed the tools the MCP server currently exposes. When
the model decides to call one, the call is forwarded to MCP, which may reach
through RPC into the open IDA database, and the result is returned to the model.

So a tool call is really a chain: **model → MCP → RPC → IDA**, and back.

## What a turn looks like

The agent streams a sequence of typed pieces. A turn where the model calls a
tool, then answers, looks like this:

```text
Calling tool 'get_function_pseudocode' with args: {"function_name": "sub_401000"}
Result: int __cdecl sub_401000(int a1) { ... }
This function validates the license key: it hashes the input and compares...
```

Each line is one typed output:

| Piece | Meaning | Renders as |
| --- | --- | --- |
| `Calling tool '...' with args: ...` | the model invoking a tool | a tool message |
| `Result: ...` | what the tool returned | a tool message |
| plain text | the model's answer | assistant text |

The two tool lines are the visible ends of that **model → MCP → RPC** chain: the
`Calling tool` line is the model's request, and `Result` is what came back after
MCP ran it against IDA.

<Callout>
Some models also stream a reasoning summary. When they do it renders as plain
assistant text prefixed `[Reasoning]:`.
</Callout>

<Callout type="warning">
The system prompt needs to tells llm which id to use. 
The model then supplies the RPC id in its tool arguments itself . If it omits or invents the id, the tool call should fail.
</Callout>

## Renderer

The renderer is the only part that writes to widgets. For each streamed piece it
decides what the UI needs: a new bubble (column), a new paragraph, or text appended to the
current paragraph.

Text and reasoning become assistant messages; tool calls and their results become
tool messages; errors become their own message. Because the orchestrator carries
the per-turn state, the renderer only has to draw.
