### Creating Plans

Your plan should roughly follow this workflow:

1) Briefly analyze the provided functions first
- Read pseudocode and any relevant data/xrefs.
- Identify candidate objects and observed accesses.

2) Check for existing structs
- Use `{ToolNames.STRUCT_LIST}` and `{ToolNames.STRUCT_GET_DEFINITION}`.
- Reuse/modify existing structs when appropriate instead of duplicating.
- If an existing struct matches semantics but has a poor name, prefer `{ToolNames.STRUCT_RENAME}` over creating a duplicate struct.

3) Create or update the main struct
- Use `{ToolNames.STRUCT_CREATE}` if no suitable struct exists.
- Add/update fields with explicit field name, type, and offset expression.
- Resolve every offset via tools; do not compute offsets mentally.
- Add/Update fields as soon as you confirmed the purpose. Do not attempt to wait till all fields are inferred for struct creation.
- Meaningful-modification rule: do not add cosmetic aliases or duplicate semantics (for example `length` at the same offset as `stringLength`).
- Before every field edit, inspect the current struct definition and prefer `{ToolNames.STRUCT_UPDATE_FIELD}` when the target offset already exists.
- Only replace an existing same-offset field when there is strong evidence of a true correction (type/semantic mismatch), not a synonym rename.

4) Infer and build child structs when evidence supports it
- If a field points to nested object layout, create/update child struct.
- Apply child struct typing where evidence is sufficient.

5) Re-verify pseudocode
- Re-open pseudocode after struct changes.
- Confirm improved readability and consistency with observed accesses.
- If verification fails, request more context instead of guessing.

## Struct Tools and Intended Use

- `{ToolNames.STRUCT_LIST}`: check whether a related struct already exists.
- `{ToolNames.STRUCT_GET_DEFINITION}`: inspect existing fields/types/offsets before edits.
- `{ToolNames.STRUCT_CREATE}`: create a base struct when needed.
- `{ToolNames.STRUCT_RENAME}`: rename an existing struct when evidence shows the current name is inaccurate or too generic.
- `{ToolNames.STRUCT_SET_SIZE}`: set explicit struct size in bytes when reliable size evidence exists.
- `{ToolNames.STRUCT_ADD_FIELD}`: add/replace a field with explicit name/type/offset expression.
- `{ToolNames.STRUCT_UPDATE_FIELD}`: rename/retype/move an existing field.
- `{ToolNames.STRUCT_APPLY_TO_VARIABLE_OR_ADDRESS}`: apply struct type to local variable/function arguments/address.
- `{ToolNames.GET_FUNCTION_PSEUDOCODE}`: retrieve function pseudocode for analysis
- `{ToolNames.GET_DATA_AT_ADDRESS}`: inspect memory/data evidence.
- `{ToolNames.GET_XREFS_TO}`: inspect usage/callers to infer related fields.

Size rule:
- Use `{ToolNames.STRUCT_SET_SIZE}` only when size can be inferred reliably (for example from clear bounds, allocator size, or consistent terminal field extent).
- If size evidence is ambiguous, do not force a size; request more context first.

Reliable size evidence examples:
- Allocator/constructor evidence: object allocated with a stable byte size used consistently for the same type.
- Bounded copy/zero patterns: repeated `memcpy`/`memset` boundaries that match the same object layout.
- Terminal field extent: highest confirmed field offset plus field width is stable across functions.
- ABI/type evidence: called APIs or typed casts imply a concrete struct size.

Ambiguous size examples (do NOT resize yet):
- Single-function evidence with uncertain pointer aliasing.
- Conflicting access ranges across different call sites.
- Sparse offsets with large unknown gaps and no allocation bound.
